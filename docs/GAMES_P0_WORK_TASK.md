# Cleos 小游戏中心 P0：井字棋与邀请 TA（交付 Work）

## 目标与范围
在 Android Compose 版 Cleos 的**主页**增加“小游戏中心”入口，首款仅实现**井字棋**，允许用户主动邀请一个已有 TA 陪玩。跑通角色选择、邀请、对局、合法动作、胜负判定、保存与恢复。暂不实现围棋、五子棋、多人联机、HTML 游戏安装或复杂游戏商店。

## 已核对的源码入口
- `ui/CleosNavHost.kt`：Compose Navigation 路由注册。
- `ui/MainScreen.kt`：现有四个底部栏目（聊天、日记、待办、主页），**不要增加第五个底栏**。
- `ui/home/HomeScreen.kt`：主页卡片布局；建议在 MemoryCard 与 FavoritesHomeCard 之间插入小游戏中心卡片，实际以最新代码为准。
- `ui/feed/FeedInviteDialog.kt`：朋友圈“邀请 TA 看看”弹窗；现有头像、名字、单选、当前 TA 优先选择、点击确认后才请求模型等交互值得复用。
- `data/FeedInteractions.kt`：朋友圈邀请记录；**不能直接复用作游戏状态存储**。

## P0 用户流程
1. 用户进入主页 → 小游戏中心 → 井字棋。
2. 初始为未邀请状态，展示“邀请 TA 一起玩”；不因打开页面自动调用 API。
3. 点击后弹出**来自真实 CompanionEntity 的角色列表**，有多个 TA 时可选一个，只有一个时可简化确认；不硬编码角色名字。
4. 用户确认邀请后，进入等待阶段。若实现“TA 接受/拒绝”，须通过已有 Provider 调用并处理失败、超时与拒绝；如工期有限，P0 可先将邀请确认视为开始对局，但 UI 必须如实表述，不能伪装成模型主动接受。
5. 用户执 X 先手，TA 执 O 后手。用户点击空格落子，本地验证并更新棋盘，检查结果；未结束时再请求 TA 的下一步。
6. TA 仅返回 **0..8 的格子索引**（或明确结构化动作），系统校验范围、空格、回合与对局 ID，校验成功才落子。非法动作允许有限重试，仍失败则提示重试，不得偷偷替 TA 下棋并声称是模型下的。
7. 横/竖/斜三连胜、九格平局、退出后恢复、重新开局、模型请求失败后重试均须可用。

## 架构边界
- **本地是唯一权威状态源**：`GameSession` 管理 sessionId、gameType、playerTaId、board、turn、status、history、revision、pendingRequest 等。棋盘与胜负判定用纯 Kotlin 逻辑，可单元测试。
- **AI 只决定行动**：模型读取局面和允许动作列表；不得直接修改本地数据库、判定胜负或通过自由文本推进回合。
- **避免并发双步**：用户回合仅能落一子；TA 请求期间锁定棋盘；响应必须匹配 sessionId、revision、当前回合，过期响应丢弃；重入和重复点击不触发双请求。
- **对局持久化**：使用项目已有 Room/数据库习惯，优先最小兼容改动；退出页面、进程重启可恢复。不要将游戏状态混入朋友圈 FeedInteractions。
- **调用与费用**：优先使用现有 TA 绑定的 Provider/模型、调用日志与用量机制。仅在明确邀请和 TA 需要行动时调用模型；避免轮询和每帧调用。
- **异常与安全**：无 TA、无 Provider、离线、API 超时、非法输出、拒绝邀请、退出中断等均有清楚反馈。绝不将 API Key 传给 HTML/WebView。P0 井字棋优先原生 Compose，不必引入 WebView。
- **复用方式**：可以抽取朋友圈选择器的 UI 组件，但不能破坏朋友圈现有邀请资格、评论选择和重复邀请逻辑；必要时先复制少量 UI 并留待后续重构。

## 分阶段交付
- **P0-A**：入口、邀请 UI、纯本地双人井字棋状态机与胜负判定、单元测试。无模型时可通过模拟对手测试，但必须显著标注“模拟”。
- **P0-B**：接入 TA Provider 的真实落子、异常重试、请求防重、用量日志。
- **P0-C**：持久化恢复、真机交互验收、回归测试与报告。
每阶段可独立提交；避免把所有功能捆成一个难审查的巨大提交。
