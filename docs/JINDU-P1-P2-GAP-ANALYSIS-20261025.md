## 前置说明
基于 Aster 的四份审计报告分析，Cleos 已有较完整的：
✓ 记忆系统（Memory.kt）：5类记忆 + 分层摘要/细节 + pinned 保护
✓ 会话摘要（Recap.kt）：滚动折叠 + 缓存优化 + 并发保护
✓ 主动消息（Later.kt）：WorkManager 调度 + 频率限制 + 宽限机制

因此 P1/P2 **不做重构**，只补实际缺口。

## P1：记忆系统补缺口
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

### 已有能力（无需改动）
- ✓ Memory.kt 已有 5 类记忆（profile/interest/recent/rapport/self）
- ✓ 分层摘要/细节（摘要120字符，细节300字符）
- ✓ pinned 记忆保护（不可自动删改）
- ✓ recent 带时间戳
- ✓ 聊天只注入摘要，细节需 memory open 工具查看

### 实际缺口（待审计 + 补充）

#### A. 重复记忆检测（优先级：中）
**现状**：未确认 Memory.kt 的 remember() 是否做重复检测
**影响**：可能产生"用户喜欢咖啡"重复存储多次
**施工计划**：
1. 审计 Memory.kt 的 remember() 实现
2. 如无检测，添加基于主题摘要相似度的去重逻辑
3. 补单测：连续存储相同记忆 → 验证不重复

#### B. 记忆冲突处理（优先级：中）
**现状**：未确认是否有冲突标注机制
**影响**："用户喜欢咖啡" vs "用户不喜欢咖啡" 可能同时存在
**施工计划**：
1. 审计 update() 方法的冲突处理
2. 如无机制，添加冲突标记字段或替换旧记忆逻辑
3. 补单测：存储冲突记忆 → 验证有标注或自动替换

#### C. 时效清理（优先级：低）
**现状**：recent 类有时间戳，但未确认是否自动清理过期记忆
**影响**：长期使用后记忆可能堆积
**施工计划**：
1. 审计是否有定期清理逻辑
2. 如无，添加基于时间戳的自动归档/清理机制
3. 补单测：模拟时间流逝 → 验证旧记忆被清理

#### D. Token 统计（已在 P0 完成）
**现状**：P0 已补 Recap/FeedAi/Letters 的 usageTag
**待确认**：Memory.kt 的模型调用是否也需要补 purpose=memory
**施工计划**：如有独立模型调用，按 P0 方式补齐

### P1 执行顺序
1. **先审计**：读 Memory.kt 源码，确认 A/B/C 哪些确实缺失
2. **提交审计报告**：列出实际缺口 + 现有能力，等玖玖确认
3. **再施工**：只补确认的缺口，不改现有架构
4. **验证**：补单测 + 编译 + 真机验证（需要触发记忆更新）

## P2：主动消息补缺口
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

### 已有能力（禁止重做）
- ✓ Later.kt 已有 WorkManager 调度
- ✓ MAX_WAITING=4（单角色待办上限）
- ✓ UNANSWERED_MAX=2（连续主动消息限制）
- ✓ SOON_MINUTES=1（正在回复时顺延）
- ✓ RETRY_MINUTES=10（失败重试）
- ✓ grace() 宽限机制（30分钟~3小时）
- ✓ ChatRepository.kt 根据 ta.proactive 开放 Later 工具

### 实际缺口（待审计 + 补充）

#### E. 静默时段（优先级：高）
**现状**：未确认是否支持"夜间免打扰"
**影响**：可能半夜发通知打扰用户
**施工计划**：
1. 审计 LaterWorker 是否有时间段检查
2. 如无，添加静默时段配置（默认 22:00~8:00 不提醒）
3. 补单测 + 真机验证（需要实际触发通知）

#### F. 唯一工作标识与重启恢复（优先级：高）
**现状**：WorkManager 需要唯一 work ID 避免重复调度
**影响**：重启后可能丢失或重复提醒
**施工计划**：
1. 审计 LaterWorker 的 work tag/ID 生成逻辑
2. 确认重启后是否正确恢复待办
3. 补真机验证：杀进程重启 → 确认提醒不丢失/不重复

#### G. 通知权限与渠道（优先级：高）
**现状**：Android 13+ 需要运行时通知权限
**影响**：无权限时主动消息无法触达
**施工计划**：
1. 审计是否有权限检查 + 请求流程
2. 审计通知渠道（NotificationChannel）配置
3. 补真机验证：拒绝权限 → 验证降级行为

#### H. Doze 与电池优化（优先级：中）
**现状**：Android Doze 模式可能延迟 WorkManager
**影响**：提醒不准时
**施工计划**：
1. 审计是否使用 setExpedited() 或 AlarmManager 兜底
2. 补真机验证：开启省电模式 → 测试提醒延迟

#### I. Token 统计（待确认）
**现状**：Later.kt 触发的模型调用可能未记 usageTag
**施工计划**：按 P0 方式审计 + 补齐

### P2 执行顺序
1. **先审计**：读 Later.kt + LaterWorker + 通知相关代码
2. **提交审计报告**：列出 E/F/G/H/I 哪些确实缺失
3. **再施工**：只补确认的缺口
4. **真机验证**（必须）：后台调度、通知权限、静默时段都需要真机测试
